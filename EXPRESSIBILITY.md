# Expressibility of the milestone-7 target

**Measured 2026-08-16.** This is the number [`STATUS.md` §9](STATUS.md) and
[`ROADMAP.md`](ROADMAP.md) both call "the single most useful unmeasured number about this
project", and [#24](https://github.com/DrDrewCain/zdeceptron/issues/24) is the issue that asked
for it.

It is separate from [`BENCHMARKS.md`](BENCHMARKS.md) on purpose. That file measures what the
emitter *costs* — DOM crossings, bytes, moves per reorder — and the table in it is generated by
`crates/zdc-bench/tests/benchmark.rs`, which rewrites the region between its markers and fails
the build when the committed text and the measurement disagree. This measures what the language
can *say*, the evidence is a source tree rather than a counter, and nothing here regenerates. Two
different questions, two documents.

---

## 1. Why every previous figure was withdrawn, and what is different here

Five figures have been quoted for this target — 0%, 16.4%, 21.3%, 24.2%, 47.6% — and an audit
established that **not one was measured on a tree that existed.** Each was either a measurement
of a commit that had since moved on, or a projection over a *union* of branches that was never
built. The one genuinely measured increment, +4.9 points, sat on top of a 16.4% projection, and
projection-plus-increment is not a measurement.

What is different is that there is now a tree. `~/zdc-portfolio` is the target rewritten in
ZDeceptron: 21 modules, 12,515 lines, a router, a blog rendered from markdown at build time, and
eleven games ported from the TypeScript originals. It is not a probe corpus assembled to be
measured. It is somebody's website, and it compiles.

So this measurement quotes a tree and a commit on both sides, and both are named below before
any number is.

## 4. What `main` is missing: one lexical rule, and six language features

### 4.1 The 358 diagnostics are one rule

Every diagnostic `main` reports on this tree falls into seven classes, and all seven are the same
sentence: a line ended where the writer meant it to continue.

| count | diagnostic |
|---:|---|
| 332 | Expected a value, found a line break. |
| 8 | Expected a line break after the statement. |
| 7 | Expected a name as an imported name, found a line break. |
| 5 | Expected a line break after the declaration. |
| 4 | Expected `)` to close a parenthesised expression. |
| 1 | This line is indented 8 spaces, which does not match any enclosing block. |
| 1 | Expected a line break after the variant. |

The rule that closes all 358 is `ee63fe5`, *"Let a line wrap, and make the formatter do it"* —
which is on four branches and not on `main`. A tree of this size writes argument lists, `use`
lists and record literals that do not fit on one line; nothing on `main` lets them wrap. It is a
layout rule, it costs the language nothing, and until it lands **`main`'s expressibility on this
target is 0% for a reason that has nothing to do with expressibility.**

That is worth stating plainly because it is the trap #24 exists to name. A measurement taken on
`main` today would report 0.0% and would be *true and useless* — the same shape of number as the
five that were withdrawn.

### 4.2 Six language features the tree needs beyond `main`

Removing the wrap rule is not sufficient. Of the 32 commits between `main` and compiler B, these
touch language surface the tree uses, with the tree's own usage counted beside each:

| Feature | Commit | Usage in the tree |
|---|---|---|
| line wrapping | `ee63fe5` | every module |
| vector elements — `Scene`, `Group`, `Path`, `Circle`, `Segment` | `868d377`, `bad5dc0` | 9 `Scene`s and 56 `Path`s in `site.zd`, drawing seven games |
| a clock that folds — `every … starting … to …` | `a0a5af7`, `203875e` | 5 of the tree's 7 clocks: the snake, the blocks, Conway, the runner and its score |
| conditional expressions | `d296dc0` | 61 sites across 7 modules |
| labelled `choice` variants | `779abb0` | `game2048.zd`'s `Direction` |
| GitHub-flavoured markdown | `a5ff633` | 7 content files carry a GFM table |
| a large `static` declared once | `cbe12ce` | 151 `static` signals, the largest being the 8,505-word list |

The same commit that brought GFM brought `from scroll`, which this tree uses **zero** times —
noted because §9 comes back to it.

The clock fold is the one worth pausing on, because it is #19-adjacent and it lands the frame
loop's *useful* half. `every frame` on `main` gives a `Decimal` nothing may write; a simulation
needs a cell whose next value is a function of its last. `a0a5af7` is that, and it is what makes
`state serpent is client Snake every "110ms" starting (newSnake of 1) to (snakeStep of serpent)`
a whole game loop in one declaration.

### What makes the comparison unfair, in both directions

**Unfair to TypeScript.** The right-hand column counts no dependency. `gray-matter`,
`next-mdx-remote`, `remark-gfm`, `next`, `react` and `react-dom` are ten production packages the
original imports and the port does not have; `posts.zd`+`frontmatter.zd` at 2.55× and
`projects.zd` at 3.22× are the two rows where that dominates, because the front-matter reader
`gray-matter` provides is written out in ZDeceptron. On the same accounting the port's runtime is
87,947 bytes of emitted JavaScript, all of it generated, and its dependency list is empty.

**Unfair to ZDeceptron.** Three of the four rows below 1.0× are shorter for a reason the language
supplies rather than a reason the writer earned. `terminal.zd` at 0.26× is the most extreme and
the least meaningful: the session is 101 lines because the games it raises live in modules that
are counted on their own rows. `life.zd` and `mines.zd` are genuinely shorter — a `Scene` with a
`viewBox` scales itself, and the original's resize arithmetic and canvas-sizing code have nowhere
to live.

**Unfair to both.** The port has **no tests**. The original has 33 test files and 4,153 lines of
them, excluded from every number above. The port's own comments argue the step functions are pure
and therefore testable, which is a claim about what could be written, not a line count.

**One row is not a port at all.** `wordle-words.ts` is 927 lines of TypeScript that is two arrays
and nothing else. In the port it is `content/terminal/words.txt` and `answers.txt` — 9,192 lines
of data read by `build read` — and `lexer.zd` is 251 lines. Counting 927 lines as "ported" by 251
is arithmetic that flatters the language for a change that any language could make. It is
included above because the original genuinely was a module and now genuinely is not; the effect
on the totals is under 1%.

## 8. The workarounds, which are the interesting datum

A workaround is a gap that did not stop the program but cost something. The port records its own,
in prose, at the site of each. These are the ones with a cost attached.

**A grid is a `Text`.** `mines.zd`, `blocks.zd`, `critters.zd`, `dungeon.zd` and `life.zd` all
represent a two-dimensional board as a flat string indexed `y * width + x` rather than as a
`List of` anything, and each says why: a `List of` a record costs a rebuild of the whole list per
change. `critters.zd`'s sprite generator is the sharpest case — the original mutates a 12×12
`number[][]` eight times over and the comment says of it, flatly, *"None of that is
expressible."* The replacement is 144 characters and each pass returns a new one. The cost is
real; the port also argues the replacement is better, because a pass reads the grid exactly as
the previous pass left it.

**Text inside a drawing.** The vector vocabulary is `Group`, `Path`, `Circle` and `Segment`, and a
string is not one of them. Every `ctx.fillText` in the originals becomes a `Text` element beside
the `Scene`. Three modules reach this independently — `dungeon.zd` moves the HUD, `mines.zd` its
status line, `dino.zd` its score and its "extinct" banner. The port notes the consolation: the
text that moved out selects and reflows, which the canvas text did not.

**One path per colour, not per cell.** `snake.zd` drops the original's per-segment alpha fade and
`blocks.zd` drops its per-tile bevel, both because the effect would cost one `Path` per cell,
which is the per-cell draw call a `Scene` exists to avoid. `dungeon.zd` gives up a per-legendary
hue for the same reason and keeps the ornament.

**No character codes.** `codebreak.zd` writes out an FNV-1a hash and the comment says there is no
`codeOf` in the prelude, so the fold has nothing to fold.

**Two clocks where one would do.** `dino.zd` declares both `every frame` and a fixed-timestep
accumulator, because `every frame` says *when* to step and not how much time has passed, and the
original's comment is emphatic that a 144 Hz display must not run the game 2.4× fast.

**A route parameter cannot enumerate over `build list`.** The tree's README records this one: the
slugs are written out while the posts themselves are read from disk, so adding a post is two
edits. `in` needs a literal `static` list.

**`assets/` is one CSS namespace.** Every stylesheet is linked into every document the project
emits. The tree prefixes its classes by hand to keep the game's `.page` away from the blog's.

**And one that dissolved.** `blocks.zd`: *"The canvas is sized to the viewport on every resize; a
`Scene` has a `viewBox` and scales itself, so the arithmetic has nowhere to live and nothing to
do."* The original's resize handling is not worked around; it stops existing. That is the shape
to look for when ranking, and §9 finds one more of it.

## 9. #19's five, measured

[#19](https://github.com/DrDrewCain/zdeceptron/issues/19) names five browser capabilities and says
this measurement is its prerequisite. Here is the evidence, by call site in the original, split by
whether the module that holds it was ported.

| capability | sites in original | in ported modules | in unported modules | still needed by |
|---|---:|---:|---:|---|
| frame loop (`requestAnimationFrame`) | 11 | 4 | 7 | `fire-hero`, `gate`, `pixel-walker`, `tmux-bar` |
| timers (`setInterval`/`setTimeout`) | 18 | 7 | 11 | 7 modules |
| observers | 2 | 0 | 2 | `fire-hero`, `tmux-bar` |
| storage (`localStorage`) | 34 | 22 | 12 | `enhancement-provider`, `music-player`, `spotify-auth` |
| storage (`sessionStorage`) | 6 | 0 | 6 | `spotify-auth` |
| outbound `fetch` | 5 | 0 | 5 | `spotify-auth`, `top-tracks`, `web-playback`, `zd-example-frame` |

### Frame loop — **used, and it works.** Rank: not needed.

Four `every frame` declarations: two folds that *are* the runner's simulation and its score, and
two plain clocks that are the runner's timestamp and the critter lab's animation phase. The fold
form is what makes a frame loop a whole game loop rather than a tick source. The seven sites in
unported modules are not blocked *by* the frame loop: `pixel-walker` and `tmux-bar` need an
observer,
`fire-hero` needs WebGL and an observer, `gate` is in the docs section that has no route. Nothing
in this target is waiting on a frame loop.

### Timers — **used, and they work.** Rank: not needed.

Three `every "…"` declarations run the snake at 110 ms, the falling blocks at 60 ms and Conway at
90 ms. `after "…"` is never used at all — the target has no "show this, then that" transition. Of
the 11 unported sites, four are `setTimeout` used as a one-shot delay in modules unported for
other reasons.

### Storage — **used, and it works, and the gap is closed by a rule rather than a feature.** Rank: not needed.

**34 `localStorage` call sites in the original collapse to 4 `remembered` declarations** — the
2048 best score, the dino best, the snake best and the crawl's deepest floor. The compression is
not an accident of counting. `critters.zd` records the design: the original persists on every
action; here the rules module carries `caught`, `growth` and `badges` as ordinary fields and *the
caller* decides whether they are remembered. A placement is a property of the program, not a call
you make.

The 12 unported sites are three modules: `enhancement-provider` is React hydration bookkeeping the
port does not want; `music-player` and `spotify-auth` are the Spotify feature.

`sessionStorage` is 6 sites in one file, and all six hold the PKCE code verifier for the OAuth
exchange. Reference §14 already ruled on exactly this: the survey behind `remembered` found
`sessionStorage` used six times against thirty for `localStorage`, *"and every one of those six
held half of an OAuth exchange — which is a `secret`, which no browser store may hold."* **This
tree is that survey's sixth case, independently.** The decision was right and needs no revisiting.

### Observers — **wanted, absent, and the only one of the five that blocks anything.** Rank: 1.

Two sites, both `IntersectionObserver`, zero `ResizeObserver`, zero `MutationObserver`:

- `fire-hero.tsx:130` — *"The hero scrolls away; there is no reason to keep simulating for it."*
  Gates a `requestAnimationFrame` loop on visibility.
- `tmux-bar.tsx:89` — a scroll spy: which of several sections is in a band of the viewport.

`from scroll` exists on compiler B and does not cover either. It gives the *document's* progress
as a `Decimal` from 0 to 100, and both of these questions are about a specific element's position.
Reference §14 says the same thing from the language's side: observers *"are per element rather
than per program, so they want an event on a view node rather than a signal, and that is the `on`
grammar."*

Two sites is a small number and it should be read carefully. Both are load-bearing for their
module and both are the *first* thing that has to be answered before either module can be
attempted — 353 lines, 2.4% of the target, blocked on a construct that does not exist. And the
first of the two is a *pause* condition, which is the class of thing that will recur for every
clock the language grows: `every frame` today runs a simulation for a canvas that scrolled off
the screen an hour ago.

### Outbound `fetch` — **absent, wanted by the target, and refused by the language on purpose.** Rank: last, and possibly never.

`request` already exists. It is not what this target needs, and the gap is a decision rather than
an omission:

| the target's 5 fetch sites | what it does | what `request` says |
|---|---|---|
| `spotify-auth.ts:78`, `:118` | `POST` to the token endpoint | no body, no method — `GET` only |
| `top-tracks.tsx:46` | `Authorization: Bearer …` | *"`Authorization: Bearer <secret>` is the shortest path from a credential to a third party, and the answer to it is that the route does not exist."* |
| `web-playback.tsx:42` | `PUT` with bearer and a JSON body | as above, twice |
| `zd-example-frame.tsx:82` | plain `GET` of a `.zd` file | expressible — and better expressed by `build read` at build time |

So four of five sites are a credentialled third-party API, which `request` refuses by design and
which the port's zero `secret` declarations confirm it never attempted. The fifth is a build-time
read wearing a fetch. **Widening `request` to carry headers and a body would, on the only
evidence this target offers, exist to let a bearer token reach `api.spotify.com`.** That is the
thing the construct was shaped to prevent. #19 should record outbound `fetch` as *specified and
declined for this target*, with §5.3a sink 4 left without a producer, rather than rank it.

## 10. The recommendation for #19

**Rank one of the five, drop two, and record two as already answered.**

1. **Observers — specify them.** The only one of the five that blocks a line of this target.
   Two `IntersectionObserver` sites, 353 lines, and a construct shape that reference §14 has
   already reasoned out: per element, so `on` grammar rather than a signal. Scope it to
   intersection only — `ResizeObserver` and `MutationObserver` have zero sites here, and
   `blocks.zd` shows why the first of those may never get one: a `Scene` that scales itself
   deleted the resize handling rather than needing an observer for it. Specify the *visibility*
   question, not the *observer* API.
2. **Frame loop — record as answered.** `every frame` plus the clock fold is what this target
   needed and it is what it used. Close this half against `a0a5af7` landing on `main`.
3. **Timers — record as answered.** Three declarations, three intervals, no `after` at all.
4. **Storage — record as answered, and record the `sessionStorage` refusal as confirmed.**
   34 call sites became 4 declarations. The six `sessionStorage` sites are one OAuth verifier,
   which is the exact case §14 already decided.
5. **Outbound `fetch` — record as declined for this target.** `request` exists and covers the one
   uncredentialled site. The other four want a bearer token in a header, which is the thing the
   construct refuses. Do not widen it on this evidence.

**And the item that outranks all five, which is not on #19 at all:** `ee63fe5`, the line-wrap
rule. It is worth zero expressibility on paper and it is worth 100% of this target in practice,
because on `main` the tree does not parse. Nothing on the browser-capability list should be ranked
above landing it.

## 11. Reproducing this

```sh
# the tree
git -C ~/zdc-portfolio rev-parse HEAD        # 8a79990

# compiler A
git checkout 8a99ff9 && cargo build --release -p zdc-cli
cd ~/zdc-portfolio && for f in *.zd; do zdc check "./$f"; done   # 358 diagnostics

# compiler B
git checkout 363b9e7 && cargo build --release -p zdc-cli
cd ~/zdc-portfolio && for f in *.zd; do zdc check "./$f"; done   # 0
zdc build ./site.zd                                              # 33 documents
```

Line counts on the original exclude `*.test.ts` and `*.test.tsx` and count `src/` only. Call-site
counts are `grep -c` over the same set. The module classification in §5 assigns every one of the
100 modules to exactly one group, and the script asserts that the groups partition the tree.
